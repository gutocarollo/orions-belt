## Achados-chave adicionais (fora da tabela, relevantes ao plano)

1. **Não existe hoje NENHUM projeto nesta máquina com harness Claude+Codex simultaneamente "completo e simétrico"** — learnhouse é o mais completo mas mesmo ele tem assimetrias reais (MCP só no `.mcp.json` do Claude, nada equivalente por-repo no `.codex/`; AGENTS.md é sync manual, não gerado). O framework portátil não pode assumir "copiar o padrão do learnhouse 1:1" — precisa resolver essas assimetrias de origem, não herdá-las.

2. **3 categorias de propagação de contexto, com força de enforcement decrescente**: (1) **hooks** (`.claude/settings.json`) = determinístico, dispara sempre, bloqueia turno se necessário (`completion-gate.py`, `ui-evidence-gate.sh`); (2) **injeção automática de arquivo-texto no boot da sessão** (CLAUDE.md do repo, `~/.claude/rules/*.md`, MEMORY.md) = sempre lido mas só "instrução", modelo pode discordar/ignorar; (3) **consulta sob demanda** (`docs/log.md`, topic files de memória, skills) = só entra em jogo se o agente decidir buscar. O configurador portátil precisa mapear CADA regra do harness-doador para a categoria correta — regras "bloqueantes de negócio" (ex.: nunca fazer migração em batch) pedem categoria (1); preferências de estilo pedem (2) ou (3).

3. **Memória de projeto (`~/.claude/projects/<slug>/memory/`) é chaveada por slug do CWD absoluto**, não por nome de repo nem por remote git. Confirmado pelos exemplos: existem slugs distintos para `-home-augusto-code-learnhouse`, `-home-augusto-code-learnhouse-apps-api`, `-home-augusto-code-learnhouse-apps-web`, `-home-augusto-code-learnhouse-netflix`, `-home-augusto-code-learnhouse-docs-commercial-relatorio-detalhado` — ou seja, rodar Claude Code de dentro de `apps/web/` em vez da raiz do repo gera um slug DIFERENTE com memória DIFERENTE e não-compartilhada. Isso é uma armadilha real para um configurador multi-repo: precisa normalizar/ancorar sempre na raiz do repo-alvo, nunca assumir CWD.

4. **Segredo em texto claro em superfície que um configurador poderia querer ler/copiar**: `~/.claude/settings.json` linha 3-4 (`GH_TOKEN`, `GITHUB_TOKEN`). Qualquer rotina de "clonar config global para novo projeto" tem que EXCLUIR explicitamente a chave `env` ou fazer allowlist de chaves seguras (`model`, `enabledPlugins`, `theme`, `effortLevel`, `tui`), nunca copiar o objeto inteiro.

5. **`central-ordens-bi` prova o caso-limite "nem repo git"** — um configurador robusto precisa de um passo 0 (`git init` ou recusa explícita) antes de instalar qualquer superfície `.claude`/`.codex`/`.agents`, porque commits/hooks/gitignore-allowlist pressupõem repositório git válido.

6. **`agent-swarm` e `guto-wiki`** (os 2 repos GitHub a unificar com harness-wiki) hoje têm ZERO overlap de superfície entre si: agent-swarm = Codex-first sem `.claude`; guto-wiki = conteúdo puro sem nenhuma superfície de agente; harness-wiki = conteúdo puro sem nenhuma superfície de agente. Ou seja, a "unificação dos 3 repos" citada no contexto do projeto não vai encontrar CONFLITO de convenção pré-existente entre eles (nenhum dos 3 tem convenção Claude hoje) — o conflito real de convenção está entre **estes 3 repos-alvo** e **o repo-doador learnhouse** (fonte do padrão a portar), não entre os 3 entre si.

7. **`docs/developers/harness-automacoes.md`** (untracked nesta sessão, referenciado em `docs/developers/README.md` Linha 5) já é uma varredura textual do harness do learnhouse ("16 scripts de hook nos 7 eventos... 12 regras hookify... 6 skills operacionais... Understand Anything") — candidato natural a FONTE de conteúdo/checklist para o `manifest.json`/config central do framework portátil, mas seu formato é tutorial-prosa para humano, não config declarativa para máquina; precisaria ser reestruturado (não reaproveitado literalmente) como fonte do configurador.
